## 三、主库损坏事故与恢复（2026-10-19）

**症状**：daily-wrap 连续三晚（10-16/17/18 23:30）崩于
`sqlite3.DatabaseError: database disk image is malformed`；漏斗零积累
（funnel_fixture_days / frozen_decisions / track2_snapshots 全 0）。

**双根因**：

1. **主库页树损坏**（`data/goalx.db`，267MB）：integrity_check 报多表
   二次引用/乱序 rowid/btreeInitPage 错误——时间窗指向 10-15/16 多
   serve 栈并存的混乱期硬杀进程。
2. **deployment 注册表冻结**：schedules 进程 10-16 01:00 启动，早于
   票 04-06 合入——flow 代码经 storage-at-'.' 是运行时新的（所以
   daily-wrap 会撞上新漏斗代码再崩在坏页上），但注册表停在启动时刻，
   track2-snapshots 的 */10 从未排上。

**恢复动作**：按 PID 全停栈 → 备份 `goalx.db.corrupt-backup-20261019`
→ `.recover` 重建（86.9 万行 SQL）→ 新库 integrity ok、schema v28
完整 → 崩溃路径冒烟（funnel-report 全链过）→ 换入 → 全栈在当前
main 重启 → track2 deployment 实火验证（07:30:00 完跑）。

## 四、运维教训（新增两条）

1. **合并后必须重启 schedules 进程**：注册表冻结在进程启动时刻，
   flow 代码运行时拉新只是半个真相——新 deployment 面（新 cron）
   不会自己出现。合 PR 后的验收动作=重启栈+对注册表。
2. **多栈并存硬杀是库损坏高危操作**：与 serve 重启姿势记忆互证——
   一会话一栈，按 PID 直杀全栈再起。
