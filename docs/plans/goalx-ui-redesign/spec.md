# goalx UI/UE 产品级重设计 · Spec

Status: ready-for-agent
Map: [map.md](map.md)（wayfinder 决策地图，未决设计票 02-09 的归属见其 Notes）

## Problem Statement

现有 `apps/web` 是工程原型：12 列大表直出全部数据，竞彩约束（同场不可串、2串1 上限、非单固只能串关）靠提交后的报错文案传达；真实回录表单内联挤在表格操作列里；开奖录入是单场表单；图表是手写内联 SVG；复核/设置是占位页；没有设计系统（颜色以原始 Tailwind 类散落各页），只有浅色主题；空状态与指标无任何引导。对开发者本人"能用"；对产品化目标（推广给其他用户）解释成本过高——陌生用户无法知道今天该做什么、指标什么含义、操作是否成功。

## Solution

升级为产品级 SaaS 分析台（基准 Linear/Vercel/Stripe Dashboard）：token 化浅/暗双主题设计系统；现有四页（今日/投注/资金/验证）重设计——规则前置到交互层、生命周期状态可见、指标附判读方向；新增三页（总览 Dashboard、历史复盘、指标词典）；zh-CN 单语。不做登录/多租户；API 只做增量变更，contract-first 流程不变。页面级设计方案由 wayfinder 票 02-09 逐一裁决，实现票在其后从雾区毕业。

## User Stories

**入门与寻路**

1. 作为新用户，我想要一个总览页告诉我今天哪些事需要处理（未锁定建议、待录开奖、待结算），这样我不需要预先了解系统结构就能开始。
2. 作为新用户，我想要每个指标悬停即可看到定义与判读方向，这样没有量化背景也能正确解读数字。
3. 作为新用户，我想要空状态说明缺什么数据、怎么补，这样空白页不会被误认为故障。
4. 作为操作者，我想要产品用语与竞彩官方术语一致（MatchCode、单固、在售/停售），这样界面与我对投注世界的认知直接对应。

**今日（机会发现）**

5. 作为操作者，我想要价值相关的 Fixture 优先于全量对照列表呈现，这样不必逐行扫 12 列找候选。
6. 作为操作者，我想要 EV 强度、资格徽章（可投/拒绝/证据未知）、数据新鲜度三套信号一眼可辨，这样能快速过滤场次。
7. 作为操作者，我想要竞彩规则（同场不可串、2串1 上限、非单固）在选择时就被传达，这样无效组合到不了提交。
8. 作为操作者，我想要浏览场次时选注篮始终可见，这样不会丢已选的腿。
9. 作为操作者，我想要过期报价与新鲜报价视觉可分，这样不会基于过期 OddsSnapshot 行动。
10. 作为操作者，我想要看到欧共识的数据链路新鲜度（源调盘时间），这样能判断共识数字的可信度。

**投注生命周期**

11. 作为操作者，我想要每注的生命周期阶段（建议→锁定/回录→结算→复盘）一目了然，这样清楚什么待办在哪。
12. 作为操作者，我想要专门的界面（而非表格内联输入）回录实际条款（金额/各腿赔率/时点），这样回录不易出错。
13. 作为操作者，我想要赛果自动同步（页内可主动触发，另有定时兜底），这样绝大多数比赛不需要手工录比分；人工只处理无效场次与更正。
14. 作为操作者，我想要开奖更正的影响预览在提交前展示全部变化，这样更正操作可预期。
15. 作为操作者，我想要操作反馈可见且持久（不是滚走的段落），这样明确知道每步是否成功。

**历史复盘**

16. 作为复盘者，我想要已结算注按时间/Competition/模式/策略版本筛选，这样能分析特定切片。
17. 作为复盘者，我想要任意筛选下的聚合盈亏与命中率，这样不必导出即可判断策略质量。
18. 作为复盘者，我想要从聚合行下钻到注明细再到 Fixture，这样能追查异常。
19. 作为复盘者，我想要历史页与验证页显式标注各自口径差异（前瞻纳入等），这样两页数字不同也不会破坏信任。

**验证**

20. 作为复盘者，我想要验证进度首屏给结论、细节降一层，这样几秒内吸收系统状态。
21. 作为复盘者，我想要收益曲线有专业交互（缩放、markline、tooltip），这样能细察回撤与阶段变化。
22. 作为复盘者，我想要 CLV、skill 等指标附判读方向（高了好还是低了好），这样不会误读健康度。

**资金**

23. 作为操作者，我想要真金余额与纸面收益视觉隔离，这样模拟收益永远不会被读成真钱。
24. 作为操作者，我想要成本摘要（credits 与人民币分列）有信息层级，这样单位经济可见。
25. 作为新用户，我想要空资金页引导首次入金记录，这样页面本身教会流程。

**横切**

26. 作为用户，我想要浅/暗双主题同等质量，这样长时间分析舒适。
27. 作为用户，我想要手机浏览器可用（查看状态、执行轻操作），这样离开桌面也能掌握系统。
28. 作为新用户，我想要可浏览的指标词典页，这样能系统学习整套指标体系。
29. 作为维护者，我想要设计 token 集中管理、页面禁止散写色值，这样主题一致性靠结构而非自觉。
30. 作为维护者，我想要 copy-in 组件不稀释我的覆盖率门槛，这样质量门反映的是我自己写的代码。
31. 作为有无障碍需求的用户，我想要全部交互元素可键盘到达、有屏幕阅读器标签，这样无鼠标也可用。

## Implementation Decisions

- **组件基座**：shadcn/ui 模式，**Base UI** 基座（2026-09-16 由 Radix 改判，理由见票 01 Comments），组件 copy-in 仓库自维护；不引运行时组件库；每次 `shadcn add` 后跑 lint:fix 对齐 Biome；`cn` 用第一方包（回退 clsx + tailwind-merge）。
- **图表**：ECharts 6 按需引入（echarts/core + echarts.use() + ComposeOption 类型收敛），自写薄 React hook 封装（init/dispose/setOption/ResizeObserver），不用 echarts-for-react。
- **设计 token**：CSS variables + Tailwind v4 `@theme`；语义 token（如 profit/loss、资格状态色）；浅/暗双主题共享同一 token 结构；盈亏用色惯例（红涨绿跌 vs 相反）是票 02 的人裁决项。
- **文案**：zh-CN 单语，文案按页/区集中为常量模块；不引 i18n 框架。
- **API**：只做增量（新端点/加字段/聚合口径），破坏性变更个别裁决；contract-first 流程不变（export→review diff→codegen 同 commit）；各页 API 需求由票 04-09 收集、票 10 汇总排期。
- **信息架构**：页面集 = 今日/投注/资金/验证（重设计）+ 总览/历史/词典（新增）+ 复核/设置（预留占位，等 M3/M4）；导航结构、命名、路由由票 03 裁决；落地顺序：设计系统 → 今日 → 总览 → 投注 → 历史 → 词典 → 验证/资金。
- **页面级设计决策**（布局、交互模式、视觉编码）归 map 票 02-09 所有，本 spec 不预设；每张设计票 resolve 后其实现票（含测试/e2e/axe）从雾区毕业。
- 进度锚点（2026-09-16）：02/03 已 resolve，其 `## Answer` 为实现事实源；05-09 的关键裁决以预裁决记录在各票 `## Comments`。
- **测试基建**：jsdom 下三件套（pointer-capture mock、ResizeObserver stub、echarts 走纯函数 option builder + mock 渲染）。
- **覆盖率**：copy-in 组件（components/ui/**）是否排除出覆盖率分母，由首张实现票决定。
- **领域词汇**：UI 用语遵循根目录 CONTEXT.md（Fixture/Competition/MatchCode/Market/Selection/OddsSnapshot）；指标呈现遵循 `.scratch/goalx-quant/glossary.md` 口径及其警示（如今日页 EV 是市场共识诊断量，非机会信号）。

## Testing Decisions

- 好的测试只测外部行为：页面渲染了什么（来自 API 数据）、用户动作导致什么可见结果；不测实现细节。
- **最高接缝：页面组件 + MSW**（既有模式，先例 today-page.test.tsx / bets-page.test.tsx 等）——user-event 驱动交互，断言可见结果（含资格徽章、错误前置等行为级表现）。
- API 接缝：openapi-fetch + 契约生成类型，msw handlers 对真实端点形状。
- E2E：Playwright 真浏览器 + axe 无障碍断言，每张新增/重设计页面补 e2e（沿用现有 e2e 套件先例）。
- 图表：option builder 作为纯函数直接单测；渲染层 mock。
- **不加新接缝**（2026-09-16 用户确认）：不做视觉回归（Playwright 截图对比）、不引 Storybook。

## Out of Scope

- 登录/账号体系/多租户/权限（产品化标准明确排除）。
- i18n 框架与双语（zh-CN 单语已定）。
- 原生移动 App（SPA 响应式覆盖移动可用即可）。
- 破坏性 API 变更（增量为主原则）。
- M3 复核线/M4 设置项的后端功能开发（属 goalx-quant 地图，本 effort 只做 UI 预留）。
- 赛果自动同步的后端源接入（500.com 彩果解析等，属 goalx-quant 地图；本 effort 只做同步面板 UI 与端点消费）。
